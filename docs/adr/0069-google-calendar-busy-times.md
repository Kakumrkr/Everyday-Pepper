# ADR-0069: Google Calendar in: a staff member's busy times block their bookable time

- **Status:** Accepted. Approved by the user at the S70 brief on 2026-11-25 ("Start with your recommendations and complete the session successfully"): D-1 split (the connect screen, the Team status, the reconnect card and the OAuth journey are S70.2); D-2 each staff member connects their own; D-3 a Google busy time binds like time off; D-4 poll freeBusy every 5 minutes, start and end only; D-5 `calendar.freebusy` only, an expired token keeps the last busy times; D-6 `fetch` and Zod, no SDK. Google's OAuth app stays in testing mode for S70–S71. **§10 (S71):** approved at the S71 brief on 2026-11-26 ("You can start with your recommendations and complete the session successfully"): D-1 split (sync-token read-back, reconciliation and conflicts are S71.2); D-2 a separate "Pepper bookings" calendar with `calendar.app.created`; D-3 the event holds the service and the client's first name, private, no contact details; D-4 the next 60 days are written on the grant.
- **Date:** 2026-11-25
- **Builds on:** ADR-0016 (the availability engine: time off is a blocker), ADR-0024 (sealed content, HKDF keys from `OUTBOX_SECRET`), ADR-0025 (the worker's periodic jobs and `job_scan`), ADR-0065/ADR-0067 (a provider behind a port, `off|sandbox|<provider>`, the sandbox only where tests may run), ADR-0010 (RLS, forced).

## Context
Phase 16's promise is that "their personal calendar blocks bookings": a barber's dentist appointment in Google Calendar must stop clients booking that hour. The engine has carried an empty `busy` input since Phase 2. Google's answers are outside input; its tokens are credentials to a person's calendar; and in testing mode Google expires refresh tokens after 7 days, so an expired token is a routine event, not an edge case.

## Decision
1. **A module behind a port.** `@pepper/google-calendar` (L2, `packages/modules/google-calendar`) owns the `CalendarProvider` port: the consent URL, the code exchange, the refresh, `freeBusy` for `primary`, and the revoke. `GoogleCalendarProvider` is a `fetch` adapter (no SDK, a 15 s timeout, every answer parsed by the contracts' schemas: `GoogleTokenResponseSchema`, `GoogleFreeBusyResponseSchema`, `GoogleIdTokenClaimsSchema`); `SandboxCalendarProvider` never leaves the machine (codes and tokens it made itself, one busy hour a day). `GOOGLE_CALENDAR_PROVIDER=off|sandbox|google`, off by default: every route is 404 and the worker reads nothing; the sandbox only where tests may run (as payments); `google` needs `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`. The endpoints were read from Google's documentation on 2026-11-25; nothing has run against real Google yet.
2. **The least access.** Scopes `openid email https://www.googleapis.com/auth/calendar.freebusy`, `access_type=offline`, `prompt=consent` (so a reconnect gets a new refresh token), `include_granted_scopes=true`. Pepper reads only when someone is busy, never an event's title, place or guests. S71 asks for event access by an incremental consent when it writes bookings.
3. **Connecting.** Only the member linked to a staff member connects that staff member's calendar (D-2). `POST /v1/calendar/google/connect` makes a 32-byte random state and a PKCE verifier; `calendar_connect_states` keeps the state's SHA-256 and the sealed verifier for 10 minutes, one per staff member (an upsert, so a double tap keeps the later); each start removes the business's expired states. Google sends the member back to the app's return page (S70.2), which posts `{ code, state }` to `POST /v1/calendar/google/callback`: the state is taken once (deleted whatever happens), must be unexpired and belong to the same business, member and staff member, then the code is exchanged (no transaction open across the call), the granted scopes must include free/busy, and the ID token's issuer, audience and expiry are checked for the account's email. The hashed one-time state is the CSRF check. PKCE (`S256`) is sent too: Google documents it for installed apps; its web-server guide doesn't list it, so S70.2's first real run confirms Google accepts it (it did, 2026-11-26: see "Built in S70.2").
4. **Tokens sealed.** `calendar_connections` keeps the refresh token and the current access token sealed with AES-256-GCM under a key derived from `OUTBOX_SECRET` (HKDF-SHA256, purpose `pepper/google-calendar-tokens`), bound to the connection's id as associated data. No token is ever in a response, a log, the audit log or the export. The api and the worker share the key, as they share the outbox's.
5. **Busy times, start and end only.** `calendar_busy_blocks` keeps a staff member's busy times from 7 days back to 60 days ahead, clipped to that window and merged (`busyBlocksOf`), replaced whole by each read. Forced RLS on all three tables; the sync's scan sees connection ids only (`job_scan('calendar')`).
6. **Binds like time off (D-3).** `slotsFor`, the one path behind the booking page, Pepper's offers, the waitlist and the team's booking and move check, passes the blocks to the engine's `busy` blocker. So a Google busy time is refused the way time off is, with the nearest free times. Bookings already made over it are not touched.
7. **Reading.** The worker's `Periodic` job lists due connections every minute (connected, last try over 5 minutes ago) and claims each by a conditional update, so two workers never read one calendar at once. A read refreshes an access token that is expired or within a minute of it, and once more after a 401. `invalid_grant` makes the connection `needs_reconnect`: its access token is dropped, its busy times kept (a stale block is safer than a double booking), it is no longer read, and the change is audited once. Other failures (`rate_limited`, `unavailable`, `bad_response`) keep everything and wait for the next pass. A token that no longer opens (the outbox secret changed) is `token_unreadable`: needs reconnecting too, and never blocks a disconnect or a reconnect. Each reconnect raises the connection's `generation`; a read's writes (the access token, the busy times, a failure) match the generation it claimed, so a read still holding the old, revoked grant can't mark the new connection refused or store the old account's times. A freeBusy answer is bounded at 50,000 entries and the soonest 6,000 merged blocks are kept; a block may run the whole 67-day window. Push channels (`events.watch`) need a public HTTPS address; they come after the domain (Phase 13).
8. **Disconnecting.** `DELETE /v1/calendar/google` removes the connection and its busy times in one transaction, then asks Google to revoke the refresh token; a failed revoke changes nothing in Pepper. Removing the member or the staff member removes the connection (cascade).
9. **Seeing it (top-up).** `GET /v1/calendar/outside-busy` gives the busy times (staff member, start, end, `source: google`) to everyone with `calendar.read`, like booked times; the week view draws them as "Busy (Google)" in the not-working shading.

10. **Bookings out (S71).** Each staff member's bookings are written as events in a calendar Pepper makes in their account, "Pepper bookings" (D-2): the scope `calendar.app.created` (Pepper's own calendars only, never the member's others) is asked for in the same consent as free/busy and is optional on Google's page; without it the connection reads busy times only (`writes_bookings` false) and More → Calendar offers "Add bookings to Google". A separate calendar also keeps Pepper's own events out of the `primary` freeBusy read, so a booking never blocks itself.
    - **The queue is a row per booking, kept by a trigger** (`calendar_event_syncs`, migration 0086). An `AFTER INSERT OR UPDATE OR DELETE` trigger on `bookings` raises the row's `version` on every change the event shows (time, status, staff member, service, client), whatever the path wrote it (the team, the booking page, Pepper, a manage link, an import, an undo), and creates the row when the staff member's connection writes bookings. This is the transactional outbox for this side effect, state-based: it commits with the booking, holds ids and versions only (no client data, no token), and a burst of changes to one booking is one write of its latest state. The `outbox_messages` table was not used because its payloads are sealed by the application (the trigger can't), and because a per-booking state row makes "the latest wins" a property of the table rather than of delivery order.
    - **The worker's calendar pass writes them** (the same `Periodic` as the reads, every `CALENDAR_POLL_MS`). A row is claimed with a lease (2 minutes) while `synced_version` differs from `version`; the booking is read as it is then; the event is removed from where it no longer belongs (a cancel, a removal, another staff member, a calendar made again) and written where it does, then the version written and the event's place (`event_connection_id`, `event_calendar_id`) are recorded. A change made during the write raised the version, so the row stays due: an older change never overwrites a newer one.
    - **One event per booking.** The event's id is `pepper` + the booking's UUID in hex (base32hex). A patch is tried when it was written there before, else an insert; Google's 409 "already exists" (a write that reached Google before a timeout, or an event deleted and kept by Google) becomes a patch; a patch of a missing event an insert. The body (`calendarEventBodyOf`) is the service and the client's first name, the start and end, `private`, `opaque`, a line saying changes are made in Pepper, and the booking id in a private extended property (for S71.2).
    - **Failures.** Rate limits, 5xx and bad answers back off 1, 2, 4… minutes up to an hour. `invalid_grant` makes the connection "needs reconnecting" (audited once, as for a read); its writes wait an hour at a time, and a reconnect makes them all due at once. A 403 that isn't a rate limit (`forbidden`: a permission taken back) also waits an hour; an event such a grant can't delete is forgotten. A booking moved off a calendar that needs reconnecting is still written to its new staff member's calendar (the old event is left for S71.2's reconciliation); only a cancel or a removal waits for that reconnect. A 404 on insert means "Pepper bookings" was deleted in Google: Google is asked to delete it too (in case it was only hidden from that call), its id is forgotten, the events it held are queued again, and it is made again at once the first time and with the backoff after that, so a Google that keeps answering 404 can't make calendar after calendar. Two workers making the calendar at once keep the first stored one and delete the other.
    - **A client deleted (ADR-0051)** has their visits' events written again without a name: `deleteClientRow` raises those rows' versions, as the trigger on `bookings` doesn't see a change to the client.
    - **The grant and the disconnect.** A connect that grants the scope queues the staff member's bookings of the next 60 days that aren't cancelled (D-4). A reconnect that unticks the bookings permission, or signs in with another Google account, forgets the old calendar and its events and asks Google to delete it with the old grant, just before that grant is revoked. Disconnect removes the connection, forgets where its events are, then (outside the transaction) refreshes once, asks Google to delete "Pepper bookings", and revokes; each Google step is best-effort.
    - **On screen (top-up).** `GET /v1/calendar/bookings/:id` (`calendar.read`; RLS: staff see their own bookings) answers `written`, `pending`, `waiting` (until the staff member reconnects) or `none`; the booking sheet says "Also in Google Calendar", "Adding to Google Calendar…" (asking again every 10 s while open, for two minutes) or "Waiting for Google Calendar to be reconnected".

## Consequences
- A booking reaches Google within one calendar pass of being saved (a minute by default, 10 s in CI). Changes made in Google to a Pepper event are not read back yet: S71.2 reads "Pepper bookings" with sync tokens and puts Pepper's version back (reconciliation), and handles conflicts.
- A change to a service's name or a client's name doesn't rewrite existing events until the booking itself changes (the trigger is on `bookings`); S71.2 can add it with reconciliation. A deleted client is the exception (above).
- Revoking the replaced grant on a reconnect (S70) may end the whole grant at Google, the new token included; S70.2's real run didn't reconnect. The real run of §10 checks a reconnect too.
- A business that is deleted leaves its staff members' "Pepper bookings" calendars in Google until each member removes them (the deletion doesn't call Google); noted for the deletion flow.
- A Google busy time can be up to 5 minutes stale; a booking in that gap is possible and accepted for the pilot. The booking page does no live Google call, so it stays fast and works when Google doesn't.
- In testing mode every staff member reconnects weekly. S70.2 makes that one tap ("Reconnect"); the user's OAuth verification ends it.
- The export leaves out the connection (its tokens are secrets) and the busy times (Google still holds them).

## Built in S70.2
- api `GET /v1/calendar/connections` (`staff.read`): each staff member's status and last read for the Team list, never the account's email (AC-X-165).
- web More → Calendar and Google's return, `/more/calendar/google`: a route handler, not a page. The web server finishes the connect with the member's cookie and the app's origin (`AUTH_BASE_URL`, new on the web server), then answers 303 to More → Calendar with `?google=<outcome>`; the code never reaches the page's script and the return is never a history entry (the review found Back restoring a stale page after a client-side `history.replaceState`). Home's "Reconnect your Google Calendar" card, worked out from the member's own status (no feed kind, D-1 of the S70.2 brief); the Team line (AC-X-160…164).
- The Google adapter sends its client in a Basic header (RFC 6749 §2.3.1), never in the token form; the sandbox's `sandbox-expired` code (needs reconnecting at the connect's first read) for the browser journeys.
- **The first real run (2026-11-26, testing mode, one test user):** the consent page asked for the email and free/busy only; Google returned `code`, `state`, `iss=https://accounts.google.com` and the granted scopes (`email`, `userinfo.email`, `openid`, `calendar.freebusy`); the code exchange **with PKCE (`S256`) and the Basic client succeeded**, the connect's own read worked ("Read just now", no busy times in the window then); after an event was added, the worker's next read stored one busy time of one hour (start and end only); Disconnect answered 204 and removed the connection. The client secret was entered only through the environment's secure credential form; the code was used once through the real return page.
