# ADR-0049: Client import: batches, matching and undo

- **Status:** Accepted (built in S48). Pre-approved by the user at the S48 brief on 2026-11-03 ("Go ahead with your recommendations and complete the session"; D-2 to D-6).
- **Date:** 2026-11-03
- **Builds on:**
  - ADR-0017 (clients: email unique per business, E.164 phones, `source` `import`; staff never write clients)
  - ADR-0003, ADR-0024, ADR-0041 (BullMQ behind a Postgres relay: the database is the truth, jobs carry ids, a lease and an attempt count make a lost or repeated job harmless)
  - ADR-0025 (`withJobScan`: a worker reads across businesses through one job's read-only policy)
  - ADR-0048 (raw uploads read with a size cap before any parsing)
  - [V1 playbook](../plan/v1-playbook.md) Phase 11, S48 and P1-13; [scorecard](../plan/scorecard.md) C13, C11

## Context
An owner moving in from Square, Booksy, Vagaro, GlossGenius or Fresha (or from their own app) has their clients in another system. Retyping them is the main reason not to switch (C13 at 2). Exports differ in format (CSV, JSON, JSONL), column names, phone formats and quality. An import must not create duplicates when run twice, must say what it couldn't take and why, must touch nothing before the owner agrees, and must be reversible, since the owner can't check 2,000 rows by eye.

## Decision
1. **A module of its own, `@pepper/imports` (L2, `packages/modules/imports`).** Pure parts: `parseImportFile` (CSV via `csv-parse` (D-2), JSON (an array of records, or the first array of records in an object, flattened to `parent.child` columns), JSONL; UTF-8, falling back to Windows-1252; at most 5 MB, 10,000 rows, 100 columns (D-5)); `suggestMapping` (a preset per tool, recognised by its headers, then header synonyms and endings, then value patterns: ≥ 80% emails or phones in the first 50 values; birthdays, notes, tags and visit columns are named as "later" (S49)); `mapRows`/`planRows` (a row's name, email, phone and external id, its reasons, and its outcome). The services run them inside the database's transactions.
2. **Staged, then committed.** An upload is parsed, mapped and planned against the business's clients and kept as an `import_batches` row (status `staged`) with its `import_rows` (cells, mapped values, outcome, reasons). Nothing touches `clients` until the owner commits. A new mapping re-plans the stored cells. A commit sets the batch `queued` and is audited (`client_import.committed`, the row count only). A staged import nobody commits is discarded after 24 hours.
3. **Matching (D-3, refined).** In file order, a row matches the client with the same external id, else the same email, else the one client with the same phone *and the same name*, else an identical row (a SHA-256 of name, email, phone and external id) of an earlier import that wasn't undone. The phone needs the name because families share a phone; a phone and name several clients share skips the row (`phone_shared`). A match only fills an empty email or phone, never overwrites. An email another client has is left out with a reason. A row that matches a client an earlier row of the file already created or matched is skipped as a duplicate. An existing client with neither email nor phone isn't matched by name alone: the preview shows the row as "create", and the owner decides.
4. **External ids are scoped by system.** `client_import_refs` maps `(system, external id)` to a client: `system` is the tool's preset, or `file:` and a digest of a file's column names, so two apps' "id 1" never meet. The digest is of names only, never of values.
5. **Reasons are for the owner.** Every invalid or skipped row says where it is (spreadsheet row, JSON item or JSONL line) and what to fix ("Row 4: the phone “555-0903” has 7 digits; a US number needs 10, with the area code."). Invalid rows are not imported. A row with a fixable field is fixed and re-imported, and the re-import finds what the first one created.
6. **The run: the worker's `imports` queue.** A relay finds `queued`/`running` batches through `job_scan('imports')` and queues one BullMQ job per batch (job id = batch id). `runImport` claims the batch for a 5-minute lease, then applies its rows in chunks of 500. Each chunk is planned again against the clients as they are by then (a client added since the preview is merged, not duplicated) and written in one transaction with the rows it applied, under a per-business advisory lock shared with undo. A run cut short continues where it stopped. After 3 attempts the batch is `failed`: what it wrote stays, can be undone, and an alert names its ids. A finished batch is audited by the system actor with counts only (`client_import.finished`).
7. **Undo by batch for 7 days (D-4).** Undo removes the clients the batch created, except those with a booking or waitlist entry since (kept and counted). It clears the emails and phones it filled where they still hold its value, and records `{ deleted, restored, kept }` (`client_import.undone`). External ids it recorded stay with clients that remain, and go with deleted ones.
8. **No raw file kept (D-5).** The upload lives only in the request. The rows' cells and client details are cleared on undo, or once the undo window is over (an hourly tidy-up in the worker). Only the identity hash, outcome and client id remain, so a later re-import still finds its clients.
9. **Access.** `clients.manage` (owners and managers) for every endpoint. The three tables are tenant-owned with forced RLS and a restrictive member scope that keeps staff out even in a member transaction. Tenant from the session only. Uploads are rate limited per member (20 per 10 minutes). The body is read with a 5 MB cap; CSV and JSONL come as text, JSON as `application/octet-stream` (an `application/json` body belongs to the JSON parser and is refused).
10. **API:** `GET /v1/imports`, `POST /v1/imports?format=`, `GET /v1/imports/:id`, `PUT /v1/imports/:id/mapping`, `POST /v1/imports/:id/commit` (202), `POST /v1/imports/:id/undo`, `DELETE /v1/imports/:id` (staged only). Refusals carry the owner's sentence: `import_rejected` (with `reason`), `import_not_ready`, `import_mapping_invalid`, `import_not_undoable`.

## Consequences
- An owner moves in without retyping. A wrong file or mapping is a tap on Undo, not a cleanup.
- The presets are reconstructed from public information and made-up fixtures. Real exports from the pilot will correct them; the smart mapping covers what a preset misses, and S56a adds an AI suggestion for the rest (column names and masked samples only).
- A staged file is up to 10,000 rows of client data in Postgres for at most 24 hours (or 7 days after a commit). It never reaches logs, the audit log or the worker's job data.
- S49 adds visits and upcoming appointments to the same batches. Modules don't import each other: it goes through appointments' published services or an event, decided in its brief.
- A new dependency: `csv-parse` (no dependencies of its own).

## Results (S48)
- Built as decided: `@pepper/imports` (56 unit tests, 99% lines; a property test that a re-import never creates a client and no two clients share an email), migration 0058 (`import_batches`, `import_rows`, `client_import_refs`; isolation suite green with the three tables), the service (24 integration tests: every fixture imports cleanly and re-imports with no duplicates, chunked runs resume, undo keeps clients booked since and leaves changed fields alone, the tidy-up, staff and other businesses refused), the worker's `ImportsRunner`, and `/v1/imports` (13 controller tests, 3 api integration tests).
