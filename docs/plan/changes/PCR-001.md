# PCR-001: Business brand color on the booking page

- **Status:** Approved
- **Date:** 2026-10-16
- **Plan version:** from 0.3 → to 0.4

## What changes and why
The public booking page (W8) shows the **business's own brand color** instead of Floty's raspberry. During onboarding (W1), the owner picks that color. Floty only appears in a small "Booking by floty" footer. This supports the identity commitment "branded booking page with no competitor listings": clients see the salon, not the software. Approved in the S2 mockup review.

## Affected parts
| Part | Impact | Compatible? | Action needed |
|---|---|---|---|
| contracts | Tenant branding schema gains `brandColor` (hex, validated) | Yes, additive and optional with a default | Add to the tenant settings Zod schema (Phase 2/4) |
| db | Tenant settings store one more optional field | Yes, additive | No migration risk. Default = Floty neutral |
| ui | Booking page reads `biz` tokens derived from `brandColor`. Contrast must still pass AA | Yes | Derive `biz` / `biz-strong` / `biz-soft` / `biz-on` in light and dark. Reject or adjust colors that fail AA (Phase 4) |
| apps/web (booking page) | Uses `biz` tokens instead of `brand` | Yes | Phase 4 |
| onboarding | Adds a color pick (suggested from website/logo when available) to the "ready" step | Yes, optional step | Phase 9 |
| templates | None | — | — |

## Compatibility strategy
Additive and optional. Tenants without a color get a neutral default. No existing contract changes shape.

## Tests proving no regression
- Unit: color → token derivation always yields AA-compliant text pairs (property test over random colors), in light and dark.
- Contract: tenant settings schema accepts a missing `brandColor` and rejects invalid hex.
- Playwright: booking page renders the tenant color. Existing booking E2E (AC-W8-1/2) stays green.
- Prototype: `docs/mockups/checks/contrast.py` covers the sample `biz` tokens.
