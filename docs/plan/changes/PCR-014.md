# PCR-014: S66 splits in two; a reschedule can't win back a kept deposit

- **Status:** Implemented
- **Date:** 2026-11-22
- **Plan version:** from 0.39 → to 0.40

## What changes and why
1. **S66 splits** (S66 brief, D-1): S66 builds the deposits backend ([ADR-0068](../../adr/0068-deposits-and-refunds.md)); a new **S66.2** builds the screens: the service's rule, the window setting, Stripe's card field on the booking page with the terms in words, and the journeys.
2. **The refund window is stored, and only moves while it is open** (S66 security review). Before this change, AC-X-117 counted the window from the booking's current time. A client inside the window could move the booking far out from their link and then cancel for a full refund, which undid the deposit. Now `booking_payments.refund_ends_at` is set when the booking is made. A client's move takes the window to the new time only while a cancel would still be refunded. The business's moves always take it along, and the business's cancels always refund (AC-X-118, unchanged).

| Plan | S66.2 row in the playbook and STATUS | yes | none |

## Compatibility strategy
All of this is additive and new in S66, which isn't merged yet. Rows booked before the column existed don't occur; if one did, the cancel falls back to the booking's current time. Pepper's AI moves pass no hook, so the window stays where it was (the owner decides).

## Tests proving no regression
- payments `deposits.int.test.ts`: the window is set when booked; a client's move inside it keeps the deposit; a client's move in time takes it along; the business's move always does.
- api `deposits.int.test.ts`: reschedule from the manage link inside the window, then cancel: the deposit is kept.
- Existing deposit, public-booking and isolation suites stay green.
